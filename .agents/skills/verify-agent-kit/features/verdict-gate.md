# Verdict gate

A fresh verifier records its verdict for an open pull request in the repository's orch ledger, bound to the head SHA and the verbatim patch ID (`git patch-id --verbatim`, so whitespace counts), and the ledger is the merge gate: right before each merge, every merging mode runs `agentic verify status`, which exits 0 only when a passing verdict covers the head and its unchanged patch. Nothing is posted to the forge. A pull request whose diff touches a policy path (`agentic verify --help` lists them) takes no passing verdict but `countersigned`: `record` refuses the others. It, and any other pull request the verifier marks `verifier-blocked` by definition, lands only when the user approves it in words, which the coordinator records as `countersigned` naming the patch the user approved; `record` refuses a countersign without a `verifier-blocked` verdict for the same patch, or whose `--patch` is not the current patch, and carries the blocked verdict's verifier and evidence into the countersign's evidence. `agentic rulesets plan` shows what applying the history backstop (no deletion, no force-push, linear history) would change. `agentic jev pr-risk` scores a pull request `low` (exit 0) or `high` (exit 3), or says it is `not scored` (exit 4); in the landing modes only `high` adds a second audit lane, and nothing holds the pull request.

## Sub-features

- `gate-usage` rejects `verify`, `rulesets`, and `jev pr-risk` without valid arguments, and the removed `verify publish` and `rulesets --tier`, exit 2.
- `gate-contract` checks the verdict list and which verdicts pass, that nothing mirrors a verdict to the forge, that the ruleset is the baseline backstop with no bypass, how the ledger picks the verdict for a head, the local gate's decisions, when a countersign may be recorded, that the patch ID keeps whitespace, and which paths are policy paths.
- `rulesets-plan` plans the ruleset with the changes the live ruleset implies, and changes nothing.
- `verify-status` reads a pull request's ledger state, and nothing from the forge.
- `verify-refuse-closed` refuses to record a verdict for a merged pull request.
- `pr-risk` scores a pull request with Jev and marks a score above 0.3 `high`, exit 3.
- `countersign-refused` refuses a countersign for a pull request no `verifier-blocked` verdict covers, and one whose `--patch` is not the current patch.
- `policy-refused` refuses a passing verdict other than `countersigned` for a pull request whose diff touches a policy path.
- `verify-record` records a verdict for an open pull request, bound to its head and patch, with the verifier's ID.
- `verify-gate` reads that verdict back through the local gate, which refuses the non-passing verdict.

## How to get to it (user POV)

- A verifier runs `agentic verify record <pr> --verdict <verdict> --evidence <path or URL>` with `AGENTIC_AGENT_ID` set.
- The agent about to merge runs `agentic verify status <pr>` and merges only on exit 0 for the head it merges.
- The coordinator runs `agentic verify record <pr> --verdict countersigned --patch <patch ID> --evidence <the user's message>` after the user approves a `verifier-blocked` pull request in words, shown its head and patch ID (only the refusals are driven: the drive never records a passing verdict).
- The coordinator runs `agentic jev pr-risk <pr>` on each verification round's head.
- The user runs `agentic rulesets plan <owner/repo>`, then `apply` to change the repository (not driven: it changes GitHub).

## Driving it with verify-kit

Preconditions:

- Drive target: `scripts/verify-kit drive RUN_ID verdict-gate [--pr N] [--merged-pr N] [--repo owner/name]`.
- The usage and contract steps need nothing. `gh` is logged in, and the repository has a merged pull request. `pr-risk` needs a TypeSafe key and a public repository. `countersign-refused`, `verify-record`, and `verify-gate` need an open pull request (`--pr`, or the newest open one). The drive checks every step whose prerequisites hold and names each missing one in its `SKIP` line.

- **Usage.** `agentic verify`, `agentic verify publish 1`, `agentic rulesets`, `agentic rulesets plan o/r --tier merge-gate`, and `agentic jev pr-risk 0` exit 2.
- **Contract.** The kit loads the driven checkout's `agentic/tools/verify/verify.ts` and `agentic/tools/rulesets/rulesets.ts` and checks: neither exports a forge status context, a status builder, a required verdict check, or a CI-check splitter; the verdicts are exactly `live-ui-verified`, `unit-test-verified`, `countersigned`, `type-check-only`, `verifier-blocked`, `verifier-failed`, and only the first three pass; the ruleset's rules are exactly deletion, non_fast_forward, required_linear_history; the ruleset is named `agentic-backstop`, targets branches, applies to the default branch (`~DEFAULT_BRANCH`, no excludes), is `active`, and has no bypass actors (compared regardless of key order), and the plan reports nothing for those settings and reports evaluate or disabled enforcement, a bypass actor (also on an otherwise correct ruleset), another branch, or an excluded branch as settings to change; the latest verdict for a head decides and a verdict for an older head is void; the gate is `none` with no verdict, `void` for another head or a changed patch, `fail` for a non-passing verdict, and `pass` for a passing or countersigned verdict on the head with its patch; a countersign is allowed over `verifier-blocked` for the same patch (also carried to a new head with that patch) and refused with no verdict, over `verifier-failed` or `type-check-only`, for another patch, or when the head's own row is not blocked; and it must name the current patch as the approved one (refused when unnamed or another), with evidence that carries the blocked verdict's verifier and evidence (`msg | verifier-blocked by v: run.log`), also when carried from a countersigned row; the patch IDs of `rm -rf /tmp/build`, `rm -rf / tmp/build`, and a re-indented line all differ; the policy paths cover a sampled file anywhere in a verification skill's directory (including the directory name itself and a differently cased one), `skills/babysit-and-ship/SKILL.md` and its `references/`, `claude/agents/autopilot-owner.md`, `agentic/tools/verify/`, `agentic/vendor/orch/`, and `agentic/bin/agentic`, and no sampled path outside them; a rename out of a verification skill's directory touches a policy path; and for a policy change, exactly `live-ui-verified` and `unit-test-verified` are refused, and nothing is refused for a change that touches no policy path. These expectations live in the kit, which verifiers run from trunk, so a pull request cannot loosen them along with the code.
- **Plans against the live ruleset.** The drive reads the repository's `agentic-backstop` ruleset through GitHub's API (`ruleset-before.json`). `agentic rulesets plan <repo>` must print no tier and no required checks, and exactly the `+rule` and `-rule` changes, and exactly the `~enforcement`, `~bypass_actors`, and `~conditions` setting changes, that the live ruleset implies (a live ruleset that still carries the retired merge-gate rules plans `-pull_request -required_status_checks`). Afterwards the live ruleset must be byte-identical.
- **Status of a merged pull request.** `agentic verify status <merged>` prints `<repo>#<merged> (MERGED, ...): ledger none ...`, nothing about the forge, and exits 1.
- **Refusal.** `agentic verify record <merged> ...` exits 1 with `verdicts are for open pull requests`, and no `ledger.tsv` appears.
- **Risk screen.** `agentic jev pr-risk <merged> --repo <repo>` prints `<repo>#<merged>: low, P(one-way door) <p> <= 0.3` and exits 0, or prints `high, P(one-way door) <p> > 0.3` and exits 3. The word, the comparison, and the exit code must agree with `p`; `not scored` (exit 4) fails this step, because a key is present and the repository public. The landing modes read `high` as "add a second audit lane", never as a hold. `agentic/tools/jev/cli.test.ts` covers `not scored` against a fake `gh`.
- **Countersign refused.** With `AGENTIC_ORCH_STORE` set to the run's `orch/`, `AGENTIC_AGENT_ID=verify-agent-kit-smoke-<RUN_ID>`, and the working directory the run's `fixture/` repository (`--repo` names the real one), `agentic verify record <open> --verdict countersigned --patch <its patch ID> --evidence <file>` exits 1 with `no verifier-blocked verdict covers patch`, and no `ledger.tsv` appears. The drive computes the patch ID from `gh pr diff`.
- **Record.** With `--pr`, the driven checkout must be at that pull request's head. Every record runs from `fixture/`, so a CLI that ignored `AGENTIC_ORCH_STORE` would write the fixture's ledger, never the real one. `agentic verify record <open> --verdict type-check-only --evidence <file>` prints `recorded type-check-only on <head>` and names no publish step. A countersign over it is refused the same way and leaves the ledger byte-identical. Then `verifier-blocked` is recorded, and a countersign over it whose `--patch` is forty zeros exits 1 with `a changed patch needs new words from the user` and leaves the ledger byte-identical. When `gh pr diff --name-only` lists a policy path for the pull request (`policy-files.txt`), `agentic verify record <open> --verdict unit-test-verified` exits 1 naming `changes the verification policy` and `countersigned`, and leaves the ledger byte-identical; otherwise the step is not attempted (`policy-passing-skipped.txt`), because `record` would accept it. No verdict this drive records can pass, and every countersign it attempts must be refused.
- **Gate.** `orch/ledger.tsv`'s last row holds the pull request, its head SHA, `patch:<its patch ID>`, and the verifier ID. `agentic verify status <open>` prints the head's first 12 characters and `ledger fail (type-check-only ...`, nothing about the forge, and exits 1: the gate refuses the merge; after the `verifier-blocked` record it prints `ledger fail (verifier-blocked ...` and exits 1. The real ledger in the checkout's git common directory is byte-identical before and after, and the fixture's ledger never appears.
- **Proof.** Evidence: `verdict-gate/NN-*.txt` for each command (the contract's values are in `NN-gate-contract.txt`), `ruleset-before.json`, `ledger.tsv` (the run's ledger after the smoke verdict) and `ledger-blocked.tsv` (after the `verifier-blocked` record); `smoke-only.txt` when the open pull request was picked rather than named.

## Gotchas

- `verify` finds the ledger through git's common directory unless `AGENTIC_ORCH_STORE` is set. Without it, a drive would write into the real repository's ledger; the drive always sets it, and fails if the real ledger changes anyway.
- `verify` asks GitHub for the pull request before it checks a verdict's arguments, so an argument error after the pull request number needs network to reach. The command name is checked first, so `verify publish` is a usage error offline.
- `rulesets plan` exits 0 whether or not changes are pending; the drive's check against the live ruleset is what shows the plan is right.
- A buggy `rulesets plan` in the driven checkout runs with the user's `gh` token. The drive detects a write to the live ruleset; it cannot prevent one. Read a diff to `agentic/tools/rulesets/cli.ts` before driving it.
- `pr-risk` sends the screened pull request's title, body, and diff to TypeSafe; it does so only for a public repository.
- `pr-risk` prints P rounded to two places; at exactly `0.30` either decision is consistent, so only the agreement of verb, comparison, and exit code is checked there.
- A passing `countersigned` verdict is never recorded here: the contract step checks when one is allowed, and `agentic/tools/verify/verify.test.ts` records and gates one against a fake `gh`.
- `rulesets apply` writes GitHub: the contract step checks what it would apply, never that it applies it.
